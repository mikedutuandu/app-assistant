# Phase 3: Ask HookPlaybook hosts the writer — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One assistant on Ask's page: Ask's engine answers account questions, the writing bot writes posts, in the same chats and history; the floating "Write with me" button and the browser session route go away.

**Architecture:** Ask's page keeps posting to `POST /api/ask/stream`. The route now picks an engine (chip/attachment/skill rules first, then one cheap model call), and for `write` it calls the bot server-to-server with a token it signs itself, re-encodes the bot's events into Ask's SSE format, and saves the answer (text + drafts) in `chat_messages` as it goes. The bot thread id **is** Ask's chat id (the bot learns to create a thread with a host-chosen id), so no mapping is stored and nothing is lost when the first event drops.

**Tech Stack:** app-assistant (FastAPI, psycopg, LangGraph, pytest); HookPlaybook in ai-mono (Next.js 16 on vinext, Cloudflare Workers, D1 + Drizzle, vitest).

**Spec:** `docs/superpowers/specs/2026-11-20-one-assistant-design.md` (sections 1–4, "Mike's answers", Phases → 3). Read sections 1, 3 and 4 before any task.

**Repos and branches:**
- Task 1: `/home/claude/app-assistant`, branch `phase-3-ask-hosts-writer` → its own PR, merged and deployed **first**.
- Tasks 2–8: `/home/claude/ai-mono`, branch `hookplaybook-ask-writer` (from origin/main 78741b0) → one PR. Read `products/hookplaybook/CLAUDE.md` before any of them.

## Global Constraints

- Merging to `main` is the whole deploy in both repos; no manual steps after a merge. Migrations only add (D1: new table, nullable/defaulted column, index). Never edit an applied migration; `shared/db/src/migrations.ts` is regenerated by `pnpm db:generate`, never by hand.
- The writer engine is **off** unless both `ASSISTANT_URL` and `ASSISTANT_TOKEN_SECRET` are set (`secret()` from `app/lib/env.ts`). Off means: no chip, no attach/voice, the router never returns `write`, Ask behaves exactly as today.
- The bot's session token never reaches the browser. It is signed server-side with `signAssistantToken(secret, {sub: workspaceId, access: "draft"})` per request.
- Every customer query filters by the viewer's workspace (`viewerOf(request)`); mutating routes check `sameOrigin(request)`; JSON routes check content type; `blockedForAdmin(viewer)` refuses writer work for an admin logged in as a customer.
- Credits: before writer work, `aiStopOf(workspaceId)`; the writer's model calls are charged by the bot through `assistant_charge` — the proxy writes **no** `ai_calls` row for them. The router's own model call is logged by `chatLogged` with step `"ask-route"` (prefix `ask`, so it lands in the Ask credits group).
- Rate limit: a writer turn takes the same `ask:hour:<ws>` slot as an Ask question (`ASK_PER_HOUR` = 30).
- Untrusted text sent to the bot (Ask's answers as `context`) is wrapped in `<data>` by the bot, like everything else it reads.
- Nothing posts to X. A writer draft is saved to HookPlaybook only when the user taps Add to Schedule (a draft waiting for their OK, never scheduled).
- UI: Ask's look (plain text answers, quiet icons, soft blocks), `app/components/ui` kit, Lucide icons, taps ≥ 44px on phones, no page wider than 390px on iPhone 13, text contrast 4.5:1, no `loading.tsx`.
- Writer answers render as React text (the existing `Markdown`), never HTML.
- No fixed English sentences inside the writing conversation (only error states are fixed text).

## Review Focus

1. **A dropped connection mid-writer-turn** (phone locks, tab closes): the answer row must not stay `queued` forever and block the chat and its delete. Expect: the row is filled from the bot's thread within about a minute of the next look, or failed with "No answer this time" after 3 minutes. → Task 5 tests `reconcileWriter`.
2. **An Ask chat that later turns into writing** (account question first, then "write a post about it"): the bot thread doesn't exist yet. Expect the first writer turn to create it with the chat id, and Ask's earlier answers to reach the bot as `context`. → Task 1 test `test_new_thread_with_host_id`, Task 4 test "first writer turn in an Ask chat sends new_thread and context".
3. **Writer engine off** (`ASSISTANT_URL` empty, today's production): Ask must behave exactly as before, no chip, no router call. → Task 3 test "router never called when writer is off", Task 6 source test.
4. **Writer answers after reload**: drafts, the Added state and the saved line must come back from `chat_messages.meta`, not only from the live stream. → Task 6 test of `writerViewOf`.
5. **Retry / Write it again / thumbs on a writer answer**: must re-ask the writer, never silently run Ask's engine with no skill. → Task 5 test "retry of a writer answer re-sends to the writer".
